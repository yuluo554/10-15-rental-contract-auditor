## 一、条文核对流程（数据可信度的根基）

### 1.1 数据底座预检（选题期硬门）

以"官方标准全文是否可直连获取"为**选题判据**而非事后发现。候选题逐个实测：

| 数据源 | HTTP | 字节数 | 可解析汉字数 | 结构计数 |
|---|---|---|---|---|
| 民法典（最高法官网） | 200 | 375,644 | 99,069 | 第 704/705/721 条各 1 处 |
| 北京条例（北京人大法规库） | 200 | 46,280 | 9,136 | "押金" 9 处；"备案" 13 处 |
| 上海条例（上海市政府官网） | 200 | 38,753 | 8,094 | "押金" 4 处；"备案" 19 处 |
| 北京押金托管办法（北京住建委） | 200 | 76,113 | 3,976 | "押金" 50 处 |

**弃选留档**：国家法律法规数据库（flk.npc.gov.cn）为 JS 渲染 SPA，程序化直连实测不可行，
**不作为数据底座**——"题好做"不等于"数据拿得到"，预检不过的题做到中途才发现等于全盘返工。

### 1.2 快照入仓纪律

- 快照由 `tools/fetch_sources.py` 从官方 URL 抓取并就地剥离标签产出，**不重写正文**（只做标签剥离与空白归一）。
- 快照是**字节冻结件**：`.gitattributes` 标 `-text`，防止克隆时 EOL 归一化让 sha256 失配。
- 台账 `data/knowledge/MANIFEST.json` 登记来源 URL / 抓取日 / sha256 / 字节数 / 汉字数。
- `fetch_sources.py --check` 重抓比对 → `SOURCES_FROZEN_OK`。

### 1.3 条款号机器推导（本项目的关键工程决策）

**绝不手抄条款号**。实测教训：用"定位短语、回溯 600 字符找最近条号"的启发式，
同一罚则短语被定位到两个不同条号（第十五条 / 第六十一条）——手抄与启发式都会引入
**不可复现的转写漂移**。

正解 = `tools/gen_rulesets.py` 的 `derive_clause()`：定位 `anchor` 在快照中的位置，
回溯到**最近的行首 `第X条`**，且**每处抽取值断言原文逐字包含**（`assert quote in snapshot_text`）。
断言失败即生成失败——这是"机器化逐字比对"，取代人工核对。

**"行首"这个限定是 M1 补上的第二个教训**：正文里的**交叉引用**也是 `第X条` 形态。
上海第六十一条的罚则正文以"违反本条例第三十七条第二款规定…"开头；按"任意位置回溯最近条号"
会把该罚则挂到**被引用的第三十七条**上（第五十九条的罚则同理被挂到第三十五条）。
条号错认让报告把罚则指向错误法条，读者按该条号核证会核不到——**比漏报更危险**。
官方快照里条号一律起于行首，故推导只认行首匹配；回归测试
`test_derive_clause_ignores_inline_cross_references` 锁死这条行为。

**同一个教训在解析层再犯一次（M2 修掉）**：`split_clauses()` 起初把**任意位置**的
`第X条` 都当条款边界，于是 `第一条 …乙方应遵守第五条关于维修的约定。` 被劈成两条，
并凭空造出一个"第五条"——条款序列错乱后，要素抽取的证据条款号错挂到**不存在的条款**上。
M2 的修复是把"行首"纪律升级为**定义位**判定：条号必须在行首，或同句内紧跟句末标点；
并用**前导触发词门**拦下"遵守/依照/依据/根据/按照/参照/符合/违反/适用/参见/本合同/本条例/本办法"
紧贴条号的形态（PDF 断行时引用恰好落在行首，光靠定义位判定拦不住）。
后者**不静默**：它正是"看着成功、实则错位"（`located=True` 但正文被劈开）的形态，
必须进"待人工确认"清单。回归测试
`test_inline_cross_reference_is_not_a_clause_boundary` / `test_wrapped_cross_reference_is_flagged_not_silent`。

**中文租期表述会漏抽（M2 修掉）**：合同常写"半年""一年半"而不是"6 个月""18 个月"。
原抽取式只认阿拉伯数字/中文数字+单位，`半年` 抽不到、`一年半` 更糟——被通用"X 年"式
吃成 `1.00`（**静默取错值**，比抽不到更危险）。漏抽会让保租房租期下限规则判 `unknown`
而非 `noncompliant`（**漏报**）。M2 把"X年半/半年"的匹配前置于通用式，并补 `两` 的中文数字。
回归测试 `test_half_year_term_does_not_lose_the_half` /
`test_half_year_term_triggers_affordable_lower_bound`（端到端锁死下限违规不被降级为 unknown）。

产物由生成器落盘并配 `--check` 位级一致守门（`RULESETS_FROZEN_OK`），禁手改。

**跨来源规则**：北京包同时引用《条例》与配套《暂行办法》两份来源，故 `quote` 的逐字断言
按规则**自己声明的 `source_id`** 取快照比对，而不是拿规则包的主快照——否则配套办法的规则
会被误判成"未挂原文"。

## 二、判定语义与门控设计（结论可信度的核心）

### 2.1 判定五态：区分"没查出问题"与"没检查过"

判定类工具最容易被攻击的假合规点，是把"没检查"说成"合规"。本项目用五态：

| 状态 | 含义 | 触发条件 |
|---|---|---|
| `compliant` | 符合 | 数值满足规则 |
| `noncompliant` | 不符合 | 数值违反；或无条件义务要素缺失 |
| `skipped` | 不适用 | **原文自带适用情形限制**（如"住房租赁企业"主体限制） |
| `unknown` | 无法判定 | 要素未观测 / 主体未知 |
| `not_assessed` | 未评估 | 整体级：无任何有效判定 |

**整体等级**：有 `noncompliant` → noncompliant；有 `unknown` → not_assessed（**保守口径**，
绝不声称合规）；全 skipped → not_assessed。

### 2.2 三条防假合规的硬口径

**（1）`skipped` 只给"原文明确写了适用情形"的项。**
北京条例第三十六条的主体是"住房租赁企业"，自然人之间的租赁不适用 → `skipped` 是**对的**。
但"合同里没写押金"不是不适用，是 `unknown`。

**（2）反向陷阱：主体未知 → `unknown` 而不是 `skipped`。**
这是比"冤枉用户"更隐蔽的镜像错误——把"应尽而未尽的义务"判成"不适用"，等于
**把"没做"记成"不用做"**，合规结论虚高。
本项目的 `_applicability()` 返回三态：`applies` / `not_applies` / `indeterminate`，
`indeterminate`（主体未知）走 `unknown` 分支。判别口诀：**"这项义务有没有前提条件？"**

**（3）无条件义务缺失 = `noncompliant`。**
民法典第七百零四条列出的合同要素，合同缺失某项 → 记不符合（severity=low，措辞"一般包括"如实引用）。
配合**要素别名表**：用条文的逐字措辞去匹配合同会把"已约定但措辞不同"误判成"缺失"，
产生**假 noncompliant**（比 unknown 更糟）——故每个要素配别名集合。
再加"文本是否可识别为租赁合同"的守卫：非合同文本判 `unknown` 而非"要素缺失"。

**（4）适用主体必须回读来源的"适用范围条"（M1 实测教训）。**
新增一条规则时，只看被引条款会漏掉**同一来源开头的适用范围限定**。
北京配套办法（京建法〔2024〕8 号）第九条讲押金托管义务，但**第二条**限定适用范围是
"本市范围内承租他人住房从事**转租业务的住房租赁企业**"。若只读第九条而把规则标成
"适用任何主体"，个人房东合同就会被判 `noncompliant`——**拿不适用于他的监管办法指责他**。

更值得记的是**它为什么没被基准抓到**：当时的样例正文恰好同时含"押金"与"退还"两个别名，
判定恒为 compliant，B2 全绿。**"基准全绿"证明不了"适用域正确"**——B2 的分子分母都建立在
"真值库恰好覆盖了这个形态"之上。补的正向手段是针对该形态**专门构造**一份样例
（个人合同 + 只含押金不含退还表述），并做变异验证（把 `applies_if` 改回 `any`，测试必须变红）。

### 2.3 义务类型分栏

法规里同一门槛可能挂**性质完全不同**的义务。北京条例第六十条：

> 住房租金明显上涨或者有可能明显上涨时，市人民政府**可以**采取涨价申报、限定租金或者租金涨幅等价格干预措施……

"**可以**"是**监管裁量权**，不是相对人的无条件义务。若混在一个布尔里输出，报告会把
监管的裁量说成企业的法定义务。

正解 = `effect` 枚举（`standing_obligation` / `periodic_obligation` / `conditional_institution`），
结论**分栏呈现**（`obligations` vs `conditional_triggers`），**频次/期限只取无条件义务栏**。

### 2.4 双重门控与作用域

一条规则有两类独立可核对的要素：**数值本身**与**条款号/原文位置**。
耦合成单一 status 的两个失败方向：条款号核不到时把已核对数值也无谓阻断；或
只看数值 status 时"悄悄当作已核对"。

正解 = 两个独立状态：`status`（数值，**唯一门控**）与 `clause_status`（条款号，只做可证性展示）。

进一步**按作用域门控**（`calc` / `check` / `quota`）：一份规则包承载多用途参数时，
"整包全 verified"当唯一门会让与判定无关的 pending 阻断整条判定路径。
关键设计：**scope 决定"是否参与判定"，不决定"是否呈现"**——quota 类仍以
`reference_rules` 进入报告的"条件触发栏"，否则报告会漏掉整类事项。

### 2.5 城市差异包的分层

城市包（京/沪）**叠加在全国层（民法典）之上**：全国层规则对任何城市都适用，
城市包补充地方特有规则，同名 `rule_id` 以城市包为准。
实测教训：首版未叠加时，租期 25 年的合同在城市包下漏判了民法典的 20 年上限——
**这正是基准 B2 抓出来的**（漏报 2 例）。

## 三、合成数据与基准设计（可信度的证据面）

### 3.1 确定性生成纪律

- **禁 stdlib `random`**：自研 SplitMix64（stdlib random 不承诺跨版本序列一致）。
- **禁 set 迭代序、禁系统时钟**：落盘产物无时间戳，两次运行逐字节一致。
- 生成器 `--check` 位级一致守门；产物整体作为**字节冻结 fixtures 入仓**。
- **EOL 门**：生成器一律 `write_bytes`（`Path.write_text(newline=)` 是 3.10+ 参数，
  3.8 通道直接 TypeError——本项目的双解释器验证实测抓到过）。

### 3.2 合成数据纪律

假姓名（"张三"式样例名）、假手机号（`19900000000` 号段）、假身份证；
植入真值显式登记在样例 JSON 的四处：`expect`（主期望）/ `also_expect`（同一注入隐含的
其余结论）/ `expect_fields`（应有值的字段 → 期望取值）/ `expect_absent_fields`（应观测不到的字段）。
后两者是 B1 算**字段级 P/R/F1** 的独立来源——缺了它们，B1 只能退化成布尔式准确率。

### 3.3 三层基准

| 套件 | 驱动 | 证明什么 |
|---|---|---|
| B1 | 样本驱动 | 要素抽取**字段级 P/R/F1**（真值侧登记应有字段） |
| B2 | 样本驱动 | 端到端判定命中率（植入真值**全量**对账，含 `also_expect`），误报率 |
| B3 | **规则驱动**（不读真值库） | 引擎在**所有有限端点**上对 |

**为什么必须分两层**：样本驱动证明"引擎在这些样本上对"，但**样本没覆盖的端点它证明不了**；
B3 从规则表推导端点做 ±精度邻域断言，专门补这个缺口。
判别 = "这个基准的分母，是否依赖真值库恰好覆盖了某个端点？"

**B1 的 P/R/F1 是真算的**（M4 修掉名实不符）：真值期望由生成器按合同入参**独立推导**，
不调用引擎抽取函数——否则引擎抽错时期望跟着一起错，探活永远绿。TP = 期望有值且引擎取到
**同一取值**；FP = 期望 absent 却抽到值，或取值不符；FN = 期望有值却抽不到。

**B2 的分母是真值登记的每条规则**（M4 修掉 `also_expect` 死数据）：只算"非 pass 集合"
会漏掉一整类错误——真值登记 `compliant` / `skipped` / `reference`、观测却是别的 pass 侧
状态时，两侧都不在非 pass 集合里，**恒不报**。

### 3.3.1 覆盖登记三件套（分母 + 分子 + 采样清单）

plan/04 §2.3 的判别口诀是"**分母（总数）和分子（采样数）都写出来了吗？只写分母就是假覆盖。**"
本项目此前**连分子都没有**（`coverage` 只有 `rule_total`），M4 补齐：

- 分母 = 逐形态规则条数（`rule_totals_by_check_type`）；
- 分子 = 真值库对该形态采样到的条数（`truth_sampling.<form>.sampled_rules`）；
- 采样清单 = 具体哪几条规则、由哪几份样例提供真值（`sampled_rule_ids` / `sample_ids`）；
- 声明 = "抽样覆盖、非逐条穷举"（`sampling_declaration`）——缺了声明，读者会把
  "逐形态登记"读成"逐条穷举过"。

三件套由 `src/rca/benchmark/coverage.py` 单一实现源实算，生成器（写规则包）、基准层
（核对登记与实算一致）、CLI（`rules --city X`）、报告（覆盖登记章节）共用一份——
避免"生成器算一套、基准再算一套"的双口径漂移。**某形态有规则却零采样件 → 基准判未达标**
（分子为 0 的形态等于没测）。

### 3.4 门槛是数据不是代码

验收门槛（达成率下限 / 误报上限 / 运行时长上限）随**规则包 manifest** 下发
（`benchmark_thresholds`），基准层只读、缺失即报配置错误（exit 2），**不回落代码默认值**——
门槛内联在引擎里就是"抄进代码的第二份真相"，调门槛要改代码。

### 3.5 可证伪探活（防"基准什么都没查"）

给每套件配探活：注入缺陷（篡改真值 / **注入坏引用规则** / 改规则边界）→
**断言 `run_benchmarks()` 真的返回非 0**（端到端，不是只断言对账函数返回非空）。

**探活的隐含前提 = 期望必须有独立来源**：期望与引擎同源时，注入缺陷两边一起变、探活永远绿。
本项目 B3 的期望锚定**独立公式推导**（直接读规则包 `op`/`value` 做算术断言），
B1 的期望锚定生成器入参（不调引擎抽取函数），都不与引擎共用通路。

**空分母不冒充通过**：误报对照零样本时 `hits(0) <= max(0)` 恒真、一致率恒 1.0——
"没查"被读成"查了没问题"。空分母分支统一 `not_enabled=true` + notes 声明 + **exit 1**。
同理，**某形态零采样件（分子为 0）也判未达标**。

### 3.6 判定语义三形态对账

基准覆盖三类易错形态：`skipped` 不冤枉用户 / 无条件义务缺失 = noncompliant /
无适用项 → not_assessed。

## 四、可复现性与交付

- **报告双轨字节确定性**：Markdown 与 XLSX 同输入逐字节一致（含跨秒）。
  XLSX 走**自写最小 OOXML writer**（`ZIP_STORED` + `create_system=0` + 固定 `date_time`），
  不引第三方库——第三方 ZIP 元数据会让字节漂移。
- **两格式内容一致是结构性质**：单一渲染源 `report_sections()`，Markdown 与 XLSX 各读它。
- **溯源完整性硬约束**：导出前断言"溯源行数 == 判定行数 + 条件触发行数"且 `rule_id` 可解析，
  不满足即**拒绝导出**——"半溯源"比"无溯源"更危险（读者以为已可核证）。
- **参数来源块**：报告本身含每项参数的发布机关 / 施行日期 / 文号 / URL / 抓取日期，
  让读者不开仓库也能核证。

### 4.1 M3 补掉的五个"看着有、其实没有"（知识规则里程碑）

M0 建了引擎骨架、M1 补齐了规则包数据与加载侧锚点门，故 M3 的实质是**逐条证成
模块②③的确定性纪律**，而非从零实现。复核中实测出五处**产物层面**的缺口——
每一处都不是"没写测试"，而是"承诺在产物里不成立"：

| # | 缺口 | 为什么危险 | 修法 |
|---|---|---|---|
| 1 | CLI JSON 无 `status_counts` | 只有 `overall_status` 时，`not_assessed` 既可能是"全不适用"也可能是"有一半没能判定"——机读消费者又把五态退化成三态 | `Result.to_dict()` 下发 `status_counts` + `overall_summary` |
| 2 | 报告判定表**没有法条原文列** | 锚点只落在 JSON 里，导出的报告是"看起来有依据但读者核不到原文"——比不判更危险 | 判定表与条件触发栏都加"法条原文"列 |
| 3 | 报告**不显示整体判定与五态计数** | 导出文件常被单独转发；只有明细表时读者无法区分"全不适用"与"部分未判定" | 输入事实节输出整体结论 + **五态全列（含 0 项）**的计数 |
| 4 | `version` 是 `SPECS` 里手写的字面量 | 版本号是"依据哪一版法规"的唯一标识；写死会与数据脱钩，报告标注的依据版本指向错原文 | `derive_version()` 从台账**机器推导**（引用来源中最晚 `effective_date`，`YYYY.MM`） |
| 5 | 报告"未启用清单"引导语只说"数值核对状态非 verified" | M1 起锚点门也往该清单塞条目（reason 为"缺锚点"），读者被告知是数值没核对、清单里却写着缺锚点——**理由与清单自相矛盾** | 引导语改为"因数值核对状态非 `verified` **或**缺锚点" |

**五态计数为什么要"全列含 0 项"**：只列非零项会让"该状态检查过但为 0"与"该状态
根本没纳入检查"长得一样——这正是五态设计要防的误读，只列非零项等于把它退化回三态。

**变异验证**：上述修复各配一条回归，逐项回退后测试确实转红
（`ALL_GUARDS_EFFECTIVE`）。其中两条（报告占位串、判定求值顺序）
在**首轮变异**中假绿——占位串仍含"整体判定"标签字样、进程内 `hash()` 对同一字符串
恒定使"多次调用一致"恒真。两处测试随即改为**绑定实际取值**与**绑定规则包顺序**，
第二轮转红。这印证了"变异验证要针对断言的实际强度，而非断言的存在"。

## 五、守门与工程防线

| 守门 | 作用 | 可证伪形态 |
|---|---|---|
| 零政策字面量门禁 | 数值只能来自规则包 | `--selftest` 阳性/阴性对照；测试内变异验证（植入数值 → 门必须红） |
| 脱敏审计 | 四模式（selftest/tracked/history/messages） | selftest 阳性（合成手机号必被检出）+ 6 条阴性对照 |
| 生成器冻结 | 禁手改数据 | `--check` 位级一致 |
| EOL 门 | 冻结件出现 CR 即失败 | 参数化断言 8 个冻结文件 |
| CI 接线守门 | workflow 可解析 / `fetch-depth: 0` / extras 覆盖测试期依赖 | 静态解析 workflow |
| GUI 分层守门 | 界面零判定逻辑（三条齐上） | AST 断言：不 import 规则层 + 无算术 + 无政策数值 |
| README 可跑通 | 引用输入由生成器保证存在 | 抽命令参数 + 真跑退出码 |

**token 运行时实算**：门禁与审计器的敏感 token 从 `git log` / `getpass` / 仓库绝对路径
**实算**，源码与留档**零词面**——门禁自己的输入也不许是代码字面量。
